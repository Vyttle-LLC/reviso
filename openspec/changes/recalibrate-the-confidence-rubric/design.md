# Design — Recalibrate the confidence rubric

## Context

`skills/reviso/references/confidence-rubric.md` is a verbatim fork of the
marketplace recipe's step-5 scale. That recipe scored PR comments on
product code, where "will this be hit in practice, and does it matter to
functionality" is a reasonable proxy for whether a comment is worth
posting.

Reviso runs on a wider surface: shell runners, agent prompts, eval
harnesses, configuration, and documentation are all reviewable material
here, and the project's own finder prompt singles out enforcement-vs-claim
gaps in exactly those artifacts as deserving explicit attention. The
inherited scale has no vocabulary for them.

The measured consequence, from the `reviso-6` diagnostic at v0.4.0: two
findings an independent reviewer confirmed real were generated by Reviso
and scored 68 and 40. Neither is a nitpick. Neither reads as critical to
functionality. The scale offers nothing in between.

`7c9c073` reached a related conclusion from the opposite direction — that
the gate scored one axis and never asked whether anyone would act — and
added an actionability precondition ahead of the bands, as a drop. It has
been held since 2026-08-09 pending the diagnosis that has now arrived.

## Goals / Non-Goals

**Goals:**

- Give verified contract and enforcement defects a place on the scale that
  reflects what they are: certainly real, permanently wrong, quietly costly.
- Separate "is this real" from "does this matter" so the two stop colliding
  near the threshold.
- Make the fork from the reference recipe explicit and documented.
- Resolve the held actionability work one way or the other.

**Non-Goals:**

- Not a threshold change. 75–79 was empty on the measured run.
- Not a change to gate position or pipeline structure — that is
  `move-judgment-to-the-orchestrator`, which this depends on.
- Not a widening of what counts as a finding. The exclusion list's
  substance is untouched; only how surviving candidates are scored changes.

## Decisions

**Name the defect class in the rubric rather than raising the floor.** The
blunt alternative — lower the threshold until these findings survive — was
rejected because it admits everything at that level, not the class we can
justify. The scores were 68 and 40; a cutoff low enough to catch the 40
would catch most of what the gate correctly rejects. Naming the class
raises exactly the findings whose defining property we can state.

**Score realness and importance separately, combine by rule.** One number
answering two questions is why a certainly-real, moderately-important
finding is indistinguishable from a coin-flip on something critical. This
is the same observation `7c9c073` made; the disagreement is only about
where the second axis acts. As a precondition that drops, it is another
veto applied before the whole picture exists. As a scoring input to the
orchestrator, it is the missing dimension.

**Keep the 0–100 shape.** The eval matcher's calibration, the feedback
payload's confidence buckets, and the `--explain` output all speak this
scale. Replacing it with an ordering plus a cutoff may be right eventually
and is noted as an open question; doing it here would couple a
calibration change to a format change and make the result unattributable.

**Treat the rubric revision as run identity.** The harness already refuses
comparisons across CLI versions and resolved model tiers, and
`measure-the-audit-tier` adds review tier to that set. A rubric change
moves the numbers as surely as a model roll does, so it belongs in the same
mechanism rather than in a comment nobody reads at comparison time.

**Depend on, and sequence after, the gate relocation.** If moving the gate
to the orchestrator recovers the 68 and the 40 on its own — because a
judge holding every candidate scores the comparative bands differently than
an isolated agent did — then the bands may need less surgery than this
proposal assumes, or none. Landing both at once would make the cause
unattributable, which is the failure mode this project has already paid
for twice.

## Risks / Trade-offs

- **Naming a class invites finders to label everything as that class** →
  the class is defined by a demonstrable property (a stated guarantee, and
  code that does not deliver it), and verification evidence must show the
  gap; a candidate that cannot exhibit both is scored normally.
- **Recalibration cost is real** — every published parity number becomes
  non-comparable → that is correct and already how the harness treats model
  and CLI rolls; `docs/evals.md` publishes the discontinuity rather than
  hiding it.
- **Two axes are harder for a model to apply consistently than one** →
  the combination rule is stated explicitly rather than left to judgment,
  and `--explain` surfaces both components so drift is visible.
- **This change may prove unnecessary** → that is the intended outcome of
  sequencing it after the gate relocation; a proposal that measurement
  retires is a good proposal.

## Migration Plan

1. Land `move-judgment-to-the-orchestrator` and run its task 6.2.
2. If `match.sh` and `extract.sh` recover, reduce this change to the
   documentation of the fork and close the rest.
3. Otherwise: revise the bands, add the rubric revision to run metadata,
   and mark existing calibration stale.
4. Re-check the judge against the calibration labels under the new bands
   before publishing any parity number.
5. Re-run the audit gold subset and confirm the two known regressions
   recover without a rise in clean-case false positives.

Rollback: the rubric is one reference file; reverting restores the prior
bands. Runs recorded under the new revision remain readable and are
correctly refused for comparison against pre-change runs in either
direction.

## Open Questions

- Should the score remain 0–100 once it is judging comparatively, or become
  an explicit ordering plus a cutoff? Deferred here to avoid coupling a
  calibration change to a format change.
- Does the feedback payload's confidence bucketing
  (`skills/reviso/feedback/build-payload.sh` validates `80s|90s|100`) need
  new buckets under a two-axis score? It is a hard validation that will
  `die` on an out-of-set value.
- Which parts of `7c9c073` survive as scoring inputs, and do its three
  additional exclusion-list entries stand independently of its precondition?
