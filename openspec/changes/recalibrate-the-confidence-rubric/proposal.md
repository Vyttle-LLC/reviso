# Recalibrate the confidence rubric

## Why

**The rubric has no band that fits the defect class Reviso advertises.**
Its 0–100 scale was forked verbatim from the marketplace recipe
(`eval/reference/code-review-recipe-2026-08-03.md:20-25`), written to triage
PR comments on product code. Its two top bands read:

- **75** — "very likely a real issue that will be hit in practice… very
  important and will directly impact the code's functionality"
- **50** — "a real issue, but it might be a nitpick or not happen very
  often in practice"

A contract gap in a shell script, a prompt, or a config file is verified
real, permanent, and quiet. It is not "very important… directly impacting
functionality", and it is not a nitpick. There is no band for it, so it
lands between them and dies.

Measured on `reviso-6` at v0.4.0, both confirmed real by an independent
reviewer, both generated by Reviso and then gated out:

| finding | score |
| --- | --- |
| `match.sh` — "matches at most once" is prompt-enforced only | 68 |
| `extract.sh` — loud-failure cross-check greps one phrasing | 40 |

This is precisely the class `agents/reviso-finder-bugs.md:19-24` names as
deserving explicit attention: "validation that checks shape but not the
property, or a grep that matches one phrasing of many, is a real bug even
in scripts and prompts." Reviso finds it, then scores it as though it were
a maybe.

**The scale also conflates two questions.** "Is this real?" and "does it
matter?" ride one number, so a certainly-real, moderately-important finding
and an uncertain, critical one collide near the middle and are
indistinguishable at the threshold. `7c9c073` ("Sharpen the precision bar",
held on `feature/termic-review-prompt`) diagnosed the same conflation and
answered it by adding an actionability precondition that *drops* findings
ahead of the bands. Held pending a diagnosis, which has now arrived and
points the other way: the axis is worth separating, but as a scoring input,
not another veto.

**Trigger:** this change is conditional. If
`move-judgment-to-the-orchestrator` recovers these two findings by relocating
the gate alone, the rubric may need nothing. That change's task 6.2 is the
decision point, and this proposal should not land before it reports.

## What Changes

- **The rubric gains an explicit band for verified contract and
  enforcement defects** — code, comments, prompts, or config that claim a
  guarantee the implementation does not deliver — placing them above the
  ship threshold when the gap is demonstrated, without requiring them to
  read as "critical to functionality".
- **Realness and importance are scored separately** and combined by a
  stated rule, so a certainly-real, moderately-important finding is no
  longer indistinguishable from an uncertain, critical one.
- **The rubric stops being "the reference recipe's rubric, given
  verbatim."** It becomes Reviso's own, with the fork documented and the
  divergence justified. **BREAKING** for the parity eval's matcher
  calibration, which currently assumes the recipe's bands.
- **The held actionability question is resolved** — kept as a scoring
  dimension available to the orchestrator, not as a finder-level or
  verifier-level drop.
- **Non-goal: the 80 threshold does not move.** The measured drops sit at
  68 and below and nothing occupied 75–79; the bands are what mis-score,
  not the cutoff.

## Capabilities

### Modified Capabilities

- `review-pipeline`: the confidence gate cites Reviso's own rubric rather
  than the reference recipe's verbatim one, and the rubric's bands
  distinguish verified contract/enforcement defects from nitpicks and from
  uncertainty.
- `parity-eval`: the matcher's calibration is re-established against the
  changed bands, and runs judged under the old calibration are marked as
  such rather than silently compared across it.

## Impact

- `skills/reviso/references/confidence-rubric.md` — the bands themselves.
- `skills/reviso/references/false-positives.md` — if any actionability
  entries from `7c9c073` are kept, they land here as scoring context rather
  than as exclusions.
- `commands/audit.md` and `commands/review.md` — the gating stage's
  description of what it is applying.
- `eval/calibration/` and `eval/runners/match.sh` — recalibration, and the
  marker distinguishing pre- and post-change runs.
- `docs/evals.md` — the fork is documented, per the repo's practice of
  publishing what it diverges on.
- **Ordering: depends on `move-judgment-to-the-orchestrator`**, which
  modifies the same `review-pipeline` requirement ("Per-finding
  verification with a confidence gate"). This change's delta is written
  against that change's resulting text and must not land before it.
- Report-only unchanged; `git commit -s`, one concern per PR,
  `markdownlint-cli2` and `lychee` must pass.
